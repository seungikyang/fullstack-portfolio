# 13단계 Git 협업

[HTML 목차](../index.html) · 학습 흐름. [문제 풀기](./problems.md) → [단계별 힌트](./hints.md) → [정답 비교](./answers.md) → [완료 체크](../student-checklist.md)

## 목표

혼자 쓰는 `add`, `commit`, `push`를 넘어 SI/SW 팀이 실제로 쓰는 협업 흐름을 익힙니다. 브랜치 전략, Pull Request, 충돌 해결, 리뷰 응대까지 다룹니다.

신입 채용에서 코드 실력보다 협업 매너로 먼저 떨어지는 경우가 많습니다. 이 단계는 그 매너의 기본을 만듭니다.

## 실행 방법

연습용 저장소를 GitHub에 하나 새로 만들고, 동일 저장소를 두 폴더에 클론해 "두 명이 협업하는 상황"을 흉내냅니다.

```bash
# 빈 저장소 하나 생성 (GitHub UI에서 생성 후)
git clone https://github.com/<your>/collab-practice.git ~/collab-practice-A
git clone https://github.com/<your>/collab-practice.git ~/collab-practice-B
```

A 폴더는 개발자 A의 작업 공간, B 폴더는 개발자 B의 작업 공간이라고 가정합니다.

## 완료 기준

- feature 브랜치를 만들어 main으로 PR을 올린 경험이 있습니다.
- 같은 줄을 두 브랜치가 동시에 수정한 충돌을 직접 해결했습니다.
- 한 번 이상 force push의 위험을 체감하고 안전한 대안(`--force-with-lease`)을 확인했습니다.
- `.gitignore`로 `.env`와 `node_modules`를 제외했습니다.
- 커밋 메시지를 의미 단위로 나눌 수 있다는 것을 직접 시연했습니다.

완료로 표시하기 전 [학습 근거 4종](../student-checklist.md#단계마다-남길-4종-근거)에 Git 명령, PR·충돌 결과, 해결한 오류, 충돌을 수정한 파일 위치를 기록합니다.

## 취업 연결

SI/SW 실무에서 Git은 다음과 같이 쓰입니다.

- 팀 규칙에 따라 main 브랜치를 보호하고 PR을 통해 변경을 검토하는 경우가 많습니다.
- 기능 단위로 브랜치를 만들고 PR로 리뷰를 받습니다.
- 충돌은 "버그"가 아니라 "두 명이 같은 곳을 만진 신호"입니다.

이 단계가 끝나면 "main 보호, feature 브랜치, PR 리뷰, 충돌 해결까지 한 사이클을 경험했다"고 설명할 수 있어야 합니다.

## 핵심 개념

- 브랜치 모델. Git Flow, GitHub Flow, Trunk-based.
- 머지 vs 리베이스. 언제 어떤 것이 더 깔끔한가.
- 충돌(conflict)이 발생하는 정확한 조건.
- `--force-with-lease`가 `--force`보다 안전한 이유.
- `.gitignore`의 작동 원리.
- 커밋 메시지 규칙. Conventional Commits 또는 한국어 동사형.

## 면접 연습

### main 브랜치 보호가 왜 필요한가요?

main 브랜치는 보통 운영 배포 기준이 되는 안정 브랜치입니다. 직접 push를 허용하면 리뷰, 테스트, 충돌 확인 없이 코드가 들어가 장애로 이어질 수 있습니다. 브랜치 보호를 걸면 PR 리뷰와 CI 통과를 강제해 팀의 최소 품질 기준을 지킬 수 있습니다.

### merge와 rebase 중 무엇을 언제 쓰나요?

merge는 브랜치의 작업 이력을 보존하면서 합치기 때문에 협업 이력을 명확히 남기고 싶을 때 좋습니다. rebase는 내 브랜치의 시작점을 최신 main 뒤로 옮겨 이력을 직선처럼 정리할 때 사용합니다. 공유된 브랜치에는 rebase를 조심하고, 개인 feature 브랜치 정리에는 rebase가 유용합니다.

### 같은 파일을 두 사람이 수정했는데 충돌이 안 났습니다. 왜 그럴까요?

Git 충돌은 같은 파일을 수정했다고 항상 나는 것이 아니라, 같은 줄이나 가까운 영역을 서로 다르게 수정했을 때 주로 발생합니다. 서로 다른 줄이나 Git이 자동 병합할 수 있는 변경이라면 같은 파일이라도 충돌 없이 merge될 수 있습니다. 그래서 충돌 여부는 파일 단위가 아니라 변경 위치와 내용에 따라 달라집니다.

### `git reset --hard`와 `git revert`의 차이를 설명해보세요.

`git reset --hard`는 현재 브랜치의 HEAD를 특정 커밋으로 옮기고 작업 파일도 그 상태로 되돌립니다. 기존 커밋 이력을 지울 수 있어 공유 브랜치에서 위험합니다. `git revert`는 기존 커밋을 취소하는 새 커밋을 만들기 때문에 이력을 보존하며 협업 브랜치에서 더 안전합니다.

### force push가 위험한 이유와 안전하게 대체하는 방법을 설명해보세요.

force push는 원격 브랜치 이력을 강제로 덮어써서 다른 사람이 올린 커밋을 사라지게 만들 수 있습니다. 개인 브랜치에서 꼭 필요할 때도 `--force-with-lease`를 쓰면 내가 모르는 원격 변경이 있을 경우 push를 막아줍니다. 팀 브랜치에서는 force push 대신 새 커밋, revert, PR 수정으로 해결하는 것이 안전합니다.

### 비밀번호가 들어간 파일을 실수로 커밋했습니다. 어떻게 대응하나요?

먼저 해당 비밀번호나 토큰을 즉시 폐기하고 새 값으로 교체합니다. 그 다음 `.gitignore`에 파일을 추가하고 저장소에서 노출된 파일을 제거합니다. 이미 원격에 올라갔다면 이력 삭제 도구를 검토하되, 이력에서 지워도 이미 유출됐다고 보고 키 회전을 완료해야 합니다.
