# 13단계 단계별 힌트

[단계 설명](./README.md) · [문제로 돌아가기](./problems.md) · [완료 체크](../student-checklist.md)

한 번에 모두 읽지 말고, 막힌 문제의 1단계부터 차례로 확인하세요.

## 1번. feature 브랜치 만들고 PR 올리기

### 1단계. 개념 환기

- 브랜치는 main과 분리된 변경 이력을 만들고 PR은 병합 전 검토 단위가 됩니다.
- 첫 push에서는 로컬 브랜치와 원격 브랜치의 추적 관계를 설정할 수 있습니다.

### 2단계. 접근 방향

- 현재 브랜치가 main인지 확인한 뒤 기능 브랜치를 만드세요.
- 한 줄 변경, stage, commit 순서로 로컬 이력을 만드세요.
- 원격에 올린 뒤 base와 compare 브랜치가 맞는지 보고 PR을 여세요.

### 3단계. Git 명령 수준

```bash
git switch -c <기능-브랜치>
git add <변경-파일>
git commit -m "<한 가지 의도의 메시지>"
git push -u origin <기능-브랜치>
```

## 2번. main 브랜치 보호 설정

### 1단계. 개념 환기

- 보호 규칙은 개인의 주의가 아니라 저장소 설정으로 병합 절차를 강제합니다.
- PR 필수와 직접 push 제한은 서로 관련 있지만 별도 설정일 수 있습니다.

### 2단계. 접근 방향

- 규칙 대상 브랜치 패턴이 실제 기본 브랜치 이름과 같은지 확인하세요.
- PR 필수 규칙을 저장한 뒤 로컬 main에서 작은 테스트 변경으로 push를 시도하세요.
- 성공 여부가 아니라 실제 원격 오류 메시지를 기록하세요.

### 3단계. 확인 지점 수준

```text
Repository Settings
→ Branches 또는 Rules
→ main 대상 규칙
→ pull request 필수
→ 직접 push 시 원격 응답 기록
```

## 3번. 충돌 만들기와 해결하기

### 1단계. 개념 환기

- Git 충돌은 두 변경을 자동으로 합칠 수 없을 때 발생합니다.
- rebase는 내 커밋을 최신 기준 브랜치 위에 다시 적용합니다.

### 2단계. 접근 방향

- 두 작업 공간이 같은 기준 커밋에서 같은 줄을 다르게 수정했는지 확인하세요.
- 충돌 표시에서 현재 기준과 내 변경을 읽고 최종 한 내용을 직접 결정하세요.
- 해결 파일을 stage한 뒤 rebase를 계속하고, 원격 갱신은 다른 사람 변경을 보호하는 옵션을 사용하세요.

### 3단계. Git 명령 수준

```bash
git fetch origin
git rebase origin/main
git status
git add <해결한-파일>
git rebase --continue
git push --force-with-lease
```

## 4번. .gitignore 적용 시점 실수

### 1단계. 개념 환기

- `.gitignore`는 아직 추적하지 않는 파일의 추가를 막지만 이미 추적 중인 파일을 자동 제거하지 않습니다.
- 파일을 로컬에는 남기고 Git 인덱스에서만 제거할 수 있습니다.

### 2단계. 접근 방향

- 먼저 `git ls-files`로 해당 파일이 추적 중인지 확인하세요.
- 인덱스에서만 제거한 뒤 `.gitignore`와 함께 커밋하세요.
- 실제 시크릿이 원격에 갔다면 이력 삭제보다 값 교체가 먼저입니다.

### 3단계. Git 명령 수준

```bash
git rm --cached <추적만-해제할-파일>
git add .gitignore
git commit -m "<추적 해제 의도>"
git ls-files
```

## 5번. 의미 있는 커밋 분리

### 1단계. 개념 환기

- 커밋은 한 문장으로 설명할 수 있는 하나의 논리적 변경 단위가 좋습니다.
- patch stage는 파일 전체가 아니라 변경 덩어리별로 stage 여부를 고릅니다.

### 2단계. 접근 방향

- 현재 diff를 기능, 스타일, 문서 같은 의도로 먼저 분류하세요.
- 첫 의도에 해당하는 hunk만 stage하고 staged diff를 확인한 뒤 커밋하세요.
- 나머지 의도도 같은 순서로 반복하세요.

### 3단계. Git 명령 수준

```bash
git diff
git add -p
git diff --staged
git commit -m "<이번 변경만 설명하는 메시지>"
```

## 6번. 안전한 force push

### 1단계. 개념 환기

- 강제 push는 원격 브랜치 이력을 로컬 기준으로 덮어쓸 수 있습니다.
- lease 옵션은 내가 마지막으로 본 원격 상태와 현재 원격 상태가 달라졌는지 확인합니다.

### 2단계. 접근 방향

- 다른 작업 공간에서 같은 브랜치에 새 커밋을 먼저 push하세요.
- 오래된 작업 공간에서 lease를 사용해 거부되는 실제 메시지를 기록하세요.
- 가져오기와 rebase 후 다시 시도해 안전한 복구 흐름을 확인하세요.

### 3단계. Git 명령 수준

```bash
git fetch origin
git rebase origin/<브랜치>
git push --force-with-lease
```

## 7번. 커밋 메시지 규칙 적용

### 1단계. 개념 환기

- 좋은 메시지는 변경 종류 또는 대상을 짧게 드러내고 실제 diff와 일치합니다.
- 팀 규칙의 가치는 형식 자체보다 일관된 검색과 변경 이력 이해에 있습니다.

### 2단계. 접근 방향

- 같은 변경 하나를 선택해 두 규칙으로 각각 한 줄을 작성하세요.
- 동료가 diff 없이 읽었을 때 무엇이 바뀌었는지 알 수 있는지 비교하세요.
- 선택한 규칙과 선택 이유를 연습 저장소 README에 짧게 남기세요.

### 3단계. 메시지 형태 수준

```text
<종류>: <변경 요약>
<대상> <행동을 나타내는 한국어 동사형>
```

3단계까지 확인한 뒤에도 막히면 마지막으로 [정답 예시와 비교하세요](./answers.md).
