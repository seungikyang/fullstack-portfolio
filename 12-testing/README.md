# 12단계 자동화 테스트

[HTML 목차](../index.html) · 학습 흐름. [문제 풀기](./problems.md) → [단계별 힌트](./hints.md) → [정답 비교](./answers.md) → [완료 체크](../student-checklist.md)

## 목표

코드가 의도대로 동작하는지 수동 확인이 아닌 자동화 테스트로 검증하는 능력을 익힙니다. SI/SW 실무에서는 인수인계와 유지보수가 잦아 "테스트가 통과해야 PR을 머지한다"는 흐름이 점점 표준이 되고 있습니다.

JavaScript 진영은 Vitest 또는 Jest, Java/Spring 진영은 JUnit 5 + MockMvc를 다룹니다. 두 진영에서 같은 함수와 API에 테스트를 작성해 비교합니다.

## 기술을 쓰는 이유와 동작 흐름

처음 보는 용어는 [전체 기술 안내서](../technology-guide.md)와 함께 읽으세요. 아래 흐름은 실습을 이해하기 위한 안내이며, 빈칸과 완료 체크는 직접 진행합니다.

| 기술 | 무엇이고, 왜 필요한가요? | 이 실습에서는 어떻게 쓰나요? |
| --- | --- | --- |
| Vitest·단언 | Vitest는 테스트 실행 도구이고, 단언은 실제 결과가 기대와 맞는지 검사하는 표현입니다. 코드를 바꿀 때 같은 확인을 반복하기 위해 씁니다. | [계산기 테스트](./starter/js/src/calculator.test.ts)가 [계산 함수](./starter/js/src/calculator.ts)의 결과와 오류를 확인합니다. |
| supertest | Express 앱에 HTTP 요청을 보내 응답을 검사하는 도구입니다. 함수 하나뿐 아니라 요청 처리 연결을 확인합니다. | [API 테스트](./starter/js/src/app.test.ts)가 [createApp](./starter/js/src/app.ts)으로 만든 앱을 호출합니다. |
| 테스트 격리·모킹 | 격리는 서로의 실행 결과가 섞이지 않게 하는 것이고, 모킹은 일부 의존 기능을 제어 가능한 대역으로 바꾸는 것입니다. 반복 가능한 검사를 돕습니다. | API 테스트는 매번 새 앱을 만들고, [알림 테스트](./starter/js/src/notification.test.ts)는 메일 함수 호출을 관찰합니다. |
| JUnit·MockMvc | Java 테스트 도구와 Spring 요청 처리 테스트 도구입니다. 다른 언어에서도 같은 검증 목적을 연습합니다. | [Java 문제](./problems.md)는 11단계에서 직접 만든 Spring 프로젝트가 있을 때 진행합니다. |

**API 테스트의 처리 순서:** 새 앱과 데이터 준비 → 테스트 요청 전송 → 실제 라우트 처리 → 응답의 상태·본문을 기대값과 비교 → 통과 또는 실패 보고. 테스트마다 앱을 새로 만들면 이전 게시글이 다음 테스트에 남는 일을 줄입니다.

**직접 관찰하기:** 실패 메시지에서 기대값과 실제값, 테스트 위치를 구분해 읽으세요. 빈칸을 채우기 전 실패는 실습의 출발점입니다. 통과만 목표로 기대값을 바꾸지 말고 함수와 API가 지켜야 할 규칙을 먼저 확인합니다. 이 방식은 Career Hub의 자동 검증과 14단계 CI로 이어집니다.

## 실행 방법

### JavaScript (Vitest)

```bash
cd 12-testing/starter/js
npm install
npm test
```

### Java (JUnit 5)

Spring Boot 프로젝트(11단계 starter)에서 진행합니다.

저장소에는 완성된 `11-java-spring/starter/board-api`가 기본 제공되지 않습니다. 11단계에서 해당 프로젝트와 Gradle wrapper를 직접 만든 경우에만 아래 JUnit 실습을 진행합니다.

```bash
cd 11-java-spring/starter/board-api
./gradlew test
```

## 취업 연결

SI/SW 실무에서 테스트는 다음과 같은 가치를 가집니다.

- 신입이 작성한 PR을 시니어가 빠르게 리뷰할 수 있게 해줍니다.
- 회귀 버그를 막아 운영 중 야간 장애를 줄입니다.
- CI/CD 파이프라인의 게이트 역할을 합니다.

JavaScript 테스트만 완료했다면 Vitest와 supertest 결과만 설명합니다. 실제 `board-api` 소스와 `./gradlew test` 통과 로그까지 있을 때만 JUnit·MockMvc 경험을 함께 설명합니다.

## 핵심 개념

- 단위 테스트 vs 통합 테스트 vs E2E 테스트의 차이.
- AAA 패턴. Arrange, Act, Assert.
- 모킹(Mocking)과 스파이(Spy).
- 테스트 더블의 종류. Stub, Mock, Fake, Dummy.
- 픽스처와 setUp/tearDown.
- 테스트 격리(test isolation). 한 테스트가 다른 테스트에 영향을 주지 않게.
- 커버리지의 함정. "커버리지 100%가 곧 버그 0"이 아닙니다.

## JS 진영 vs Java 진영 비교

| 개념         | Vitest/Jest               | JUnit 5                      |
| ------------ | ------------------------- | ---------------------------- |
| 테스트 정의  | `test('...', () => {})`   | `@Test void name() {}`       |
| 단언         | `expect(x).toBe(y)`       | `assertEquals(y, x)`         |
| 모킹         | `vi.mock(...)`, `vi.fn()` | `Mockito.mock(...)`, `@Mock` |
| 라이프사이클 | `beforeEach`, `afterEach` | `@BeforeEach`, `@AfterEach`  |
| API 호출     | `supertest(app).get(...)` | `MockMvc.perform(get(...))`  |
| 실행         | `npm test`                | `./gradlew test`             |

### R12-03. 테스트가 가끔만 실패하는 경우(flaky test) 어떻게 진단하나요?

테스트가 가끔만 실패하는 경우(flaky test) 어떻게 진단하나요?

보기 중 알맞은 설명 또는 답변 방식 하나를 고르세요.

1. 테스트가 가끔 실패하면 무조건 제품 버그가 없다.

3. flaky test는 테스트 이름의 길이만으로 결정된다.
4. 항상 sleep 시간을 무한히 늘리면 근본 원인이 제거된다.

### R12-04. 커버리지 100%인데 버그가 있을 수 있나요?

커버리지 100%인데 버그가 있을 수 있나요?

보기 중 알맞은 설명 또는 답변 방식 하나를 고르세요.

1. 100%이면 모든 요구 사항이 자동으로 증명된다.
2. 커버리지는 테스트가 요구한 결과의 정확도를 직접 계산한다.
3. 실행된 코드 비율이 높아도 잘못된 단언·빠진 입력·경계 시나리오로 버그가 남을 수 있다.
4. 100% 커버리지는 보안 취약점이 없다는 인증이다.
