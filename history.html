2026.07.17 · 개발 주소 3000 고정

Career Hub 프론트엔드는 포트 충돌이 있어도 3001 이상으로 이동하지 않고 항상 http://localhost:3000을 사용합니다.

충돌 프로세스 자동 종료

npm run dev:web과 npm run preview를 시작하기 전에 3000번을 수신 중인 PID를 찾아 종료합니다. 직접 정리할 때는 npm run dev:stop을 사용합니다.

다음 포트 이동 금지

Vite 개발 서버와 preview에 port: 3000과 strictPort: true를 함께 적용했습니다. 종료 권한이 없으면 주소를 바꾸지 않고 오류로 중단합니다.

운영체제별 PID 탐색

macOS·Linux는 lsof와 fuser, Windows는 netstat와 taskkill을 사용합니다. 정확히 3000번을 수신하는 프로세스만 대상으로 삼습니다.

연결 설정 동기화

CORS 기본값, 환경 변수 예시, API smoke test, 개발용 Docker 포트와 실행 문서를 모두 3000번으로 맞췄습니다. Express API는 기존 5100번을 유지합니다.

왜 수정했는가

기존 저장소는 17개 학습 단계와 풍부한 취업 문서를 갖추고 있었지만, 첫 진입 경로와 실제 취업 행동의 기록 방식이 분산되어 있었습니다. Career Hub도 지원 현황과 프로젝트는 관리했지만 목표와 주간 행동을 작성하는 워크북은 아니었습니다.

수정 전

  • 처음 읽을 문서가 여러 개라 시작 순서를 판단하기 어려웠습니다.
  • 진도 명령은 일부 코드의 빈칸 개수만 보여줬습니다.
  • Career Hub의 첫 화면은 바로 지원 현황 입력 폼이었습니다.
  • 목표 직무, 이번 주 행동, 준비 상태, 회고를 저장할 수 없었습니다.

수정 후

  • START-HERE.md 한 곳에서 목표와 경로를 정합니다.
  • 코드 빈칸과 취업 준비 체크 진행률을 분리해 확인합니다.
  • Career Hub의 첫 화면에서 취업 워크북을 작성합니다.
  • 준비도와 다음 행동이 지원·프로젝트 데이터와 함께 갱신됩니다.

무엇을 바꿨는가

기존 17개 학습 단계와 지원·프로젝트 CRUD는 유지했습니다. 취업 워크북 목적에 직접 영향을 주는 시작 경로, 기록, 측정, 검증에 변경을 집중했습니다.

1. 작성 가능한 취업 워크북

목표 직무, 목표 지원일, 이번 주 목표, 다음 행동, 주간 회고를 사용자별로 저장합니다. 이력서·포트폴리오·자기소개·모의 면접 준비 상태도 같은 화면에서 체크합니다.

2. 행동 근거 기반 준비도

막연한 자기 평가 대신 목표 설정, 이번 주 실행, 제출 자료, 실제 지원·설명을 합친 네 단계 근거로 준비도를 계산합니다.

3. 사용자별 API와 영속 저장

GET /api/workbook과 PATCH /api/workbook을 추가했습니다. 입력 검증, JSON 저장소, OpenAPI 명세, 단위·통합·smoke test까지 같은 범위로 확장했습니다.

4. 단일 시작점과 다음 단계 안내

지원까지 남은 기간별 경로를 START-HERE.md에 정리했습니다. npm run progress는 취업 준비의 네 구간과 다음 미완료 항목을 안내합니다.

5. 빈 상태와 다음 행동

지원 또는 프로젝트 기록이 없을 때 빈 화면만 보여주지 않고, 목표 직무 설정과 첫 공고·프로젝트 등록으로 이어지는 문구를 제공합니다.

6. 테스트 기반 복구와 보안 정리

누락된 React Testing Library 의존성을 복구하고 워크북 상호작용 테스트를 추가했습니다. 개발 도구를 호환 범위 안에서 갱신해 npm audit 취약점을 0개로 정리했습니다.

자동 검증 밖의 환경 확인은 아직 남아 있습니다.

Docker Compose 플러그인과 MySQL 서버가 없어 두 실행 환경은 정적 구성과 문서까지만 확인했습니다. HTML 목차는 인앱 브라우저의 데스크톱·모바일 크기에서 확인했지만 Safari·Firefox 등 브라우저별 픽셀 비교는 남아 있습니다. Career Hub의 JSON 저장소는 단일 프로세스 학습용이며, 서버 인스턴스를 여러 개 띄우는 운영에는 적합하지 않습니다. 제출용 데이터는 영속 볼륨 또는 외부 DB에서 재시작 후 다시 조회해야 합니다. 12단계의 10개 테스트와 09단계 typecheck는 학습자가 빈칸을 채우기 전에는 의도대로 실패합니다.
