# 16단계 웹 보안 기초

[HTML 목차](../index.html) · 학습 흐름. [문제 풀기](./problems.md) → [단계별 힌트](./hints.md) → [정답 비교](./answers.md) → [완료 체크](../student-checklist.md)

## 목표

OWASP Top 10 중 신입 개발자가 가장 흔히 만드는 보안 실수와 그 방어법을 직접 코드로 익힙니다. 6단계에서 다룬 비밀번호 해시·JWT는 인증 한 축에 불과합니다. 이 단계에서는 인증 외에 입력 검증·출력 인코딩·요청 위조·환경 분리까지 다룹니다.

SI/SW 실무에서 보안 사고는 곧 계약과 신뢰의 문제로 직결됩니다. "보안은 시니어 일"이 아니라 "모두의 일"이라는 감각을 가지는 게 이 단계의 목표입니다.

## 실행 방법

```bash
cd 16-security
npm install
npm run check
```

`npm run check`는 다섯 JavaScript 파일의 문법만 검사합니다. 각 문제는 취약 상태 실행 → 공격 재현 → 서버 종료 → 방어 TODO 작성 → 같은 요청 재검증 순서로 진행합니다.

| 실습          | 실행 명령                     | 포트 | 추가 준비                                                  |
| ------------- | ----------------------------- | ---- | ---------------------------------------------------------- |
| 저장형 XSS    | `npm run start:xss-stored`    | 3000 | 문제 1의 취약 출력 상태를 먼저 만듭니다.                   |
| 반사형 XSS    | `npm run start:xss-reflected` | 3000 | 문제 2의 취약 출력 상태를 먼저 만듭니다.                   |
| SQL Injection | `npm run start:sqli`          | 3000 | MySQL과 `starter/03-sql-injection-setup.sql`이 필요합니다. |
| CSRF          | `npm run start:csrf`          | 4000 | curl cookie jar로 두 경로를 비교합니다.                    |
| CORS          | `npm run start:cors`          | 3000 | 허용·거부 Origin을 비교합니다.                             |

3000번을 쓰는 실습은 동시에 실행할 수 없습니다. 한 실습의 확인을 마치면 `Ctrl+C`로 종료한 뒤 다음 명령을 실행합니다. SQL과 CSRF의 준비·검증 명령은 [problems.md](./problems.md)에 있습니다.

## 완료 기준

- [ ] `npm run check`가 통과했습니다.
- [ ] XSS, SQL Injection, CSRF의 취약 요청과 방어 후 요청 결과를 각각 기록했습니다.
- [ ] CORS의 허용 Origin과 거부 Origin 응답 차이를 확인했습니다.
- [ ] 시크릿 노출 대응 순서를 실제 비밀값이 아닌 연습용 값으로 정리했습니다.
- [ ] OWASP Top 10 항목을 자기 말로 한 줄씩 설명할 수 있습니다.
- [ ] `npm audit --omit=dev` 결과를 확인했습니다.

완료로 표시하기 전 [학습 근거 4종](../student-checklist.md#단계마다-남길-4종-근거)에 서버·공격 명령, 취약·방어 결과, 해결한 오류, 바꾼 방어 코드 위치를 기록합니다.

## 취업 연결

SI/SW 실무에서 보안은 다음과 같이 평가됩니다.

- 보안 검토가 있는 조직에서는 입력 검증과 출력 인코딩의 코드 위치를 설명하는 능력이 도움이 됩니다.
- 인증, 권한, 시크릿 처리처럼 변경 위험이 큰 코드는 검증 방법을 함께 남기는 습관이 중요합니다.
- 실제 보안 점검을 수행하지 않았다면 "점검을 통과했다"고 표현하지 않고 실습한 공격과 방어 결과만 설명합니다.

취약 요청과 방어 후 요청의 명령·응답을 모두 남긴 경우에만 "XSS, SQL Injection, CSRF의 차이와 방어 결과를 코드로 확인했다"고 설명합니다.

### "이 API는 입력 검증을 어디에서 하나요?"라고 물으면 어떻게 답하나요?

요청이 서버에 들어온 직후 라우터나 검증 미들웨어에서 body, params, query 값을 먼저 검증한다고 답하면 됩니다. 검증을 통과한 값만 서비스 로직으로 넘기고, 실패하면 400 계열 상태 코드와 명확한 오류 메시지를 반환합니다. 프론트엔드 검증은 사용자 경험을 돕는 보조 수단이고, 실제 보안 기준은 서버 검증이라고 설명하는 것이 중요합니다.

## 핵심 개념

- OWASP Top 10. 매년 갱신되는 가장 자주 발생하는 웹 취약점 목록.
- XSS. 저장형(Stored), 반사형(Reflected), DOM-based.
- SQL Injection. 파라미터화 쿼리(prepared statement)가 사실상 유일한 정답.
- CSRF. SameSite 쿠키, CSRF 토큰.
- CORS. 같은 출처 정책을 누가 어디서 검증하는가.
- 시크릿 관리. 환경 변수, `.env`, 시크릿 매니저.
- 의존성 보안. `npm audit`, `gradle dependencyCheck`.
- 비밀번호 정책. 6단계의 bcrypt와 work factor.

## 면접 연습

### XSS의 세 종류를 차이점과 함께 설명해보세요.

저장형 XSS는 악성 스크립트가 DB나 게시글에 저장됐다가 다른 사용자에게 실행되는 방식입니다. 반사형 XSS는 URL이나 요청 값에 담긴 스크립트가 서버 응답에 바로 반사되어 실행됩니다. DOM-based XSS는 서버 응답보다 브라우저의 JavaScript가 DOM을 잘못 조작하면서 발생합니다.

### prepared statement는 어떻게 SQL Injection을 막나요?

prepared statement는 SQL 구조와 사용자 입력값을 분리합니다. 사용자 입력은 SQL 코드로 해석되지 않고 값으로만 바인딩됩니다. 그래서 입력값에 `' OR '1'='1` 같은 문자열이 들어와도 쿼리 조건을 바꾸는 코드가 아니라 단순 값으로 처리됩니다.

### CSRF는 XSS와 무엇이 다른가요? 둘 중 어느 것이 더 위험하다고 보나요?

XSS는 공격자가 사용자의 브라우저에서 스크립트를 실행하게 만드는 공격입니다. CSRF는 사용자가 로그인된 상태라는 점을 이용해 원치 않는 요청을 보내게 만드는 공격입니다. 둘 다 위험하지만 XSS는 토큰 탈취, 화면 조작, CSRF 유도까지 가능하므로 피해 범위가 더 넓어질 수 있습니다.

### CORS는 누가 검증하나요? 서버가 응답 헤더만 안 보내면 안전한가요?

CORS는 브라우저가 서버 응답의 CORS 헤더를 보고 프론트엔드 JavaScript의 응답 접근을 허용할지 결정하는 정책입니다. 서버가 헤더를 안 보내면 브라우저 JS에서 응답을 읽기 어렵지만, curl이나 서버 간 요청 자체를 막는 인증 수단은 아닙니다. 따라서 CORS는 보조 방어이고, 실제 보안은 인증, 권한 검증, CSRF 방어, 입력 검증으로 해야 합니다.

### 비밀번호를 해시할 때 salt가 왜 필요한가요? bcrypt와 SHA-256의 차이는?

salt는 같은 비밀번호도 서로 다른 해시가 나오게 만들어 rainbow table 공격과 대량 비교를 어렵게 합니다. SHA-256은 빠른 범용 해시라 비밀번호 저장에는 너무 빠릅니다. bcrypt는 salt를 포함하고 의도적으로 느리게 설계되어 brute force 비용을 높이므로 비밀번호 저장에 더 적합합니다.

### `.env`를 GitHub에 푸시했습니다. 어떤 절차로 대응하나요?

먼저 노출된 키와 비밀번호를 즉시 폐기하고 새 값으로 교체합니다. 저장소에서는 `.env`를 삭제하고 `.gitignore`에 추가한 뒤 `.env.example`만 남깁니다. 이미 원격에 올라간 값은 노출됐다고 가정해야 하므로 이력 삭제보다 키 회전과 접근 로그 확인이 우선입니다.

### JWT 토큰이 탈취됐다고 의심됩니다. 어떻게 대응하나요?

먼저 영향을 받은 사용자의 토큰을 무효화하거나 서버의 JWT secret을 교체해 기존 토큰을 만료시킵니다. Refresh token을 쓴다면 해당 토큰을 폐기하고 재로그인을 요구합니다. 추가로 로그를 확인해 비정상 요청을 차단하고, 토큰 저장 위치, 만료 시간, HTTPS, XSS 방어를 점검합니다.
