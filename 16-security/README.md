## 목표

OWASP Top 10 중 신입 개발자가 가장 흔히 만드는 보안 실수와 그 방어법을 직접 코드로 익힙니다. 6단계에서 다룬 비밀번호 해시·JWT는 인증 한 축에 불과합니다. 이 단계에서는 인증 외에 입력 검증·출력 인코딩·요청 위조·환경 분리까지 다룹니다.

SI/SW 실무에서 보안 사고는 곧 계약과 신뢰의 문제로 직결됩니다. "보안은 시니어 일"이 아니라 "모두의 일"이라는 감각을 가지는 게 이 단계의 목표입니다.

## 기술을 쓰는 이유와 동작 흐름

처음 보는 용어는 [전체 기술 안내서](../technology-guide.md)와 함께 읽으세요. 아래 흐름은 실습을 이해하기 위한 안내이며, 빈칸과 완료 체크는 직접 진행합니다.

아래 starter는 방어 전후를 비교하는 로컬 실습 코드입니다. 완성된 서비스 보안 구현으로 간주하지 말고, [문제의 준비·검증 순서](./problems.md)에 따라 연습용 값으로 관찰합니다.

| 기술·개념 | 무엇이고, 왜 필요한가요? | 이 실습에서는 어떻게 쓰나요? |
| --- | --- | --- |
| XSS·출력 인코딩 | XSS는 입력한 내용이 브라우저에서 코드로 실행되는 공격입니다. 출력 인코딩은 해당 출력 위치에서 특수 문자를 글자로 다루게 하는 변환입니다. | [저장형 XSS](./starter/01-xss-stored.js)에서 HTML에 넣는 제목·본문 처리를 비교합니다. |
| SQL 파라미터화 | SQL 명령의 구조와 입력값을 분리해 전달하는 방법입니다. 사용자 입력이 검색 조건 자체를 바꾸는 문제를 줄입니다. | [SQL 실습](./starter/03-sql-injection.js)의 두 검색 경로를 MySQL에서 비교합니다. |
| 쿠키·CSRF 토큰 | 쿠키는 브라우저가 조건에 맞는 요청에 붙이는 값이고, CSRF는 이 성질을 악용한 요청 위조입니다. CSRF 토큰은 별도 확인값으로 요청을 검사하게 합니다. | [CSRF 서버](./starter/04-csrf-demo/protected.js)의 세션 확인과 토큰 확인 단계를 구분합니다. 이 서버의 세션 확인은 쿠키 존재만 검사하는 학습용 모형입니다. |
| CORS·출처 | 출처는 프로토콜·호스트·포트의 조합입니다. CORS는 다른 출처의 브라우저 코드가 응답을 읽을 수 있는지 정하는 규칙입니다. | [CORS 실습](./starter/05-cors.js)에서 요청의 출처와 허용 목록을 비교합니다. 사용자 신원·권한 검사는 별도입니다. |

**저장형 XSS를 관찰하는 순서:** 입력 전송 → 서버에 내용 저장 → 다른 조회 요청 → 서버가 HTML 응답 생성 → 브라우저가 응답을 해석. 저장할 때와 출력할 때는 다른 시점이므로, 어느 단계에서 내용이 실행 가능한 코드가 되는지 따라가 봅니다.

**직접 관찰하기:** 같은 입력을 방어 전후에 보내 화면·응답이 어떻게 달라졌는지 기록하세요. `check` 명령은 문법 검사이므로 통과만으로 방어 성공을 증명하지 않습니다. Career Hub의 인증·입력 검증·응답 처리도 각각 어떤 문제를 막는지 나누어 설명합니다.

## 실행 방법

```bash
cd 16-security
npm install
npm run check
```

`npm run check`는 다섯 JavaScript 파일의 문법만 검사합니다. 각 문제는 취약 상태 실행 → 공격 재현 → 서버 종료 → 방어 TODO 작성 → 같은 요청 재검증 순서로 진행합니다.

| 실습          | 실행 명령                     | 포트 | 추가 준비                                                  |
| ------------- | ----------------------------- | ---- | ---------------------------------------------------------- |
| 저장형 XSS    | `npm run start:xss-stored`    | 3000 | 문제 1의 취약 출력 상태를 먼저 만듭니다.                   |
| 반사형 XSS    | `npm run start:xss-reflected` | 3000 | 문제 2의 취약 출력 상태를 먼저 만듭니다.                   |
| SQL Injection | `npm run start:sqli`          | 3000 | MySQL과 `starter/03-sql-injection-setup.sql`이 필요합니다. |
| CSRF          | `npm run start:csrf`          | 4000 | curl cookie jar로 두 경로를 비교합니다.                    |
| CORS          | `npm run start:cors`          | 3000 | 허용·거부 Origin을 비교합니다.                             |

3000번을 쓰는 실습은 동시에 실행할 수 없습니다. 한 실습의 확인을 마치면 `Ctrl+C`로 종료한 뒤 다음 명령을 실행합니다. SQL과 CSRF의 준비·검증 명령은 [problems.md](./problems.md)에 있습니다.

## 취업 연결

SI/SW 실무에서 보안은 다음과 같이 평가됩니다.

- 보안 검토가 있는 조직에서는 입력 검증과 출력 인코딩의 코드 위치를 설명하는 능력이 도움이 됩니다.
- 인증, 권한, 시크릿 처리처럼 변경 위험이 큰 코드는 검증 방법을 함께 남기는 습관이 중요합니다.
- 실제 보안 점검을 수행하지 않았다면 "점검을 통과했다"고 표현하지 않고 실습한 공격과 방어 결과만 설명합니다.

취약 요청과 방어 후 요청의 명령·응답을 모두 남긴 경우에만 "XSS, SQL Injection, CSRF의 차이와 방어 결과를 코드로 확인했다"고 설명합니다.

서버 API의 입력 검증 위치와 프론트 검증의 역할을 고르세요. — 알맞은 설명 또는 답변 방식을 고르세요.

## 핵심 개념

- OWASP Top 10. 웹 애플리케이션의 주요 보안 위험 범주를 정리한 자료.
- XSS. 저장형(Stored), 반사형(Reflected), DOM-based.
- SQL Injection. SQL 구조와 입력값을 분리하는 파라미터화 쿼리를 중심으로 방어합니다.
- CSRF. SameSite 쿠키, CSRF 토큰.
- CORS. 같은 출처 정책을 누가 어디서 검증하는가.
- 시크릿 관리. 환경 변수, `.env`, 시크릿 매니저.
- 의존성 보안. `npm audit`, `gradle dependencyCheck`.
- 비밀번호 정책. 6단계의 bcrypt와 work factor.

### R16-03. CSRF는 XSS와 무엇이 다른가요? 둘 중 어느 것이 더 위험하다고 보나요?

CSRF는 XSS와 무엇이 다른가요? 둘 중 어느 것이 더 위험하다고 보나요?

보기 중 알맞은 설명 또는 답변 방식 하나를 고르세요.

1. XSS는 모든 상황에서 CSRF보다 반드시 피해가 작다.

4. 두 공격은 이름만 다르고 원인과 방어가 항상 같다.

### R16-05. 비밀번호를 해시할 때 salt가 왜 필요한가요? bcrypt와 SHA-256의 차이는?

비밀번호를 해시할 때 salt가 왜 필요한가요? bcrypt와 SHA-256의 차이는?

보기 중 알맞은 설명 또는 답변 방식 하나를 고르세요.

1. salt는 같은 비밀번호의 해시를 다르게 하고 bcrypt의 조절 가능한 비용은 빠른 범용 SHA-256보다 추측 비용을 높인다.
2. salt는 복호화 키라 DB 유출 시 원문 비밀번호를 되돌린다.
3. SHA-256이 빠르므로 비밀번호 대입 공격도 반드시 느려진다.
4. bcrypt 비용을 높이면 같은 비밀번호의 입력 길이가 바뀐다.
