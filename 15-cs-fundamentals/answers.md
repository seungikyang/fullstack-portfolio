# 15단계 CS 기초 모범 답안

자기 답안을 먼저 작성한 뒤에만 보세요. 모범 답안은 "한 가지 정답"이 아니라 "면접에서 통하는 답안의 한 예시"입니다.

각 답안은 1분 안에 말할 수 있는 길이로 정리했습니다.

## 네트워크

### N1. TCP와 UDP의 차이

TCP는 연결 지향 프로토콜로 3-way handshake로 연결을 맺고, 패킷의 순서 보장과 재전송으로 신뢰성을 제공합니다. 대신 헤더와 연결 관리 비용 때문에 UDP보다 느립니다. UDP는 비연결형이고 신뢰성을 보장하지 않지만 헤더가 작고 빠릅니다. 웹 요청(HTTP)·이메일·파일 전송은 TCP, 실시간 게임·DNS 질의·음성/영상 스트리밍은 UDP를 씁니다.

연결. 4단계 게시판 API의 HTTP 요청은 모두 TCP 위에서 동작합니다.

### N2. 3-way handshake가 필요한 이유

양쪽이 서로의 송수신 능력을 확인하고, 시퀀스 번호를 합의하기 위해 SYN → SYN+ACK → ACK 세 단계를 거칩니다. 두 단계로 줄이면 클라이언트가 서버의 ACK를 받지 못한 채 데이터를 보내거나, 오래된 SYN이 도착해 잘못된 연결이 맺힐 수 있습니다.

연결. 이 과정 자체는 OS와 네트워크 스택이 처리하므로 4단계 코드에서는 보이지 않지만, 연결 지연이 길 때 `connect ECONNREFUSED` 같은 에러로 만나게 됩니다.

### N3. HTTP와 HTTPS의 차이

HTTPS는 HTTP를 TLS 위에서 동작시킨 것입니다. 전송 구간이 암호화돼 도청과 변조를 막고, 서버 인증서로 상대를 확인합니다. TLS handshake는 1) 클라이언트 hello, 2) 서버 hello + 인증서, 3) 키 교환과 세션 키 생성, 4) 암호화 통신 시작 순서로 진행됩니다.

연결. 7단계 배포에서 Render나 Vercel은 자동으로 HTTPS를 적용합니다. 직접 인증서를 관리하지 않아도 되는 이유가 여기에 있습니다.

### N4. 클라이언트가 URL을 입력하고 화면을 보기까지

1. 브라우저가 URL을 파싱하고 DNS로 도메인을 IP로 변환합니다.
2. TCP 3-way handshake로 서버와 연결을 맺고, HTTPS면 TLS handshake를 추가합니다.
3. HTTP 요청을 보내고 서버가 HTML을 응답합니다.
4. 브라우저가 HTML을 파싱하며 CSS·JS·이미지 등을 추가로 요청합니다.
5. DOM·CSSOM·렌더 트리를 만들고 화면을 그립니다.

연결. 3단계 React 앱도 이 과정을 거쳐 첫 화면이 그려진 뒤 클라이언트 JS가 인터랙션을 담당합니다.

### N5. 쿠키 vs 세션 vs 토큰

쿠키는 브라우저가 자동으로 보내는 작은 키-값 저장소입니다. 세션은 서버가 메모리·DB에 사용자 상태를 저장하고 쿠키로 세션 ID만 식별합니다. 토큰(JWT)은 사용자 정보를 토큰 자체에 담아 서버가 상태를 저장하지 않습니다. 토큰은 수평 확장이 쉽지만 토큰 폐기가 어렵습니다.

연결. 6단계와 Career Hub는 JWT 토큰을 씁니다. 서버에 세션 저장소 없이도 인증이 동작하는 이유입니다.

### N6. CORS는 왜 존재하는가

같은 출처 정책은 한 출처(`scheme + host + port`)의 스크립트가 다른 출처의 응답을 읽지 못하게 막아, 악성 사이트가 사용자의 다른 사이트 데이터를 훔치지 못하게 합니다. CORS는 서버가 명시적으로 "이 출처는 허용한다"고 응답 헤더로 알려, 정당한 cross-origin 요청을 가능하게 합니다.

연결. 08 Career Hub의 vite 프록시 + 같은 출처 호출 패턴이 정확히 이 문제를 피하는 방식입니다.

## 운영체제

### O1. 프로세스와 스레드

프로세스는 독립된 메모리 공간을 가진 실행 단위이고, 스레드는 한 프로세스 안에서 메모리를 공유하는 실행 흐름입니다. 컨텍스트 스위칭은 스레드가 더 가볍습니다. 프로세스 간 통신은 IPC(파이프, 소켓)로, 스레드 간 통신은 공유 메모리로 가능하지만 race condition을 조심해야 합니다.

연결. Node.js는 단일 프로세스에 이벤트 루프 한 개로 동작하고, 무거운 CPU 작업은 worker_threads로 분리합니다.

### O2. race condition과 deadlock

race condition은 두 흐름이 공유 자원을 동시에 수정해 결과가 실행 순서에 따라 달라지는 현상입니다. deadlock은 두 흐름이 서로의 자원을 기다리며 영원히 멈춘 상태입니다. deadlock의 네 가지 조건은 상호 배제, 점유와 대기, 비선점, 순환 대기입니다.

연결. 4단계 메모리 게시판에서 두 요청이 동시에 같은 id의 글을 수정하면 race condition이 생깁니다. DB 트랜잭션이나 lock으로 해결합니다.

### O3. 스택과 힙의 차이

스택은 함수 호출과 지역 변수가 저장되는 영역으로 LIFO로 자동 정리됩니다. 힙은 런타임에 동적으로 할당하는 영역으로 명시적 해제 또는 GC가 필요합니다. 재귀가 너무 깊어지면 스택 오버플로, 객체를 계속 만들고 참조를 유지하면 힙 메모리 누수가 발생합니다.

연결. 3단계 React에서 컴포넌트 재귀 트리가 깊어지면 React가 fiber 구조로 콜 스택을 우회합니다.

### O4. 동기 vs 비동기, 블로킹 vs 논블로킹

동기/비동기는 호출자가 결과를 직접 기다리는지의 축, 블로킹/논블로킹은 호출이 즉시 반환되는지의 축입니다. Node.js의 fs.readFile(콜백)은 비동기 논블로킹, readFileSync는 동기 블로킹입니다.

연결. 4단계 Express 핸들러를 `async`로 쓰면 await가 비동기 블로킹처럼 보이지만, 그 사이 이벤트 루프는 다른 요청을 처리합니다.

### O5. 가상 메모리

OS가 프로세스에 연속된 큰 주소 공간을 제공하기 위해 페이지 단위로 물리 메모리에 매핑합니다. 메모리가 부족하면 LRU 같은 알고리즘으로 페이지를 디스크로 옮겼다(swap) 다시 가져옵니다. 페이지 교체가 너무 잦아지면 CPU가 일을 못하고 페이지 작업만 하는 thrashing이 발생합니다.

연결. 운영 서버 메모리가 부족할 때 응답이 갑자기 느려지는 증상의 원인 중 하나가 thrashing입니다.

## DB 이론

### D1. ACID의 네 가지 속성

Atomicity는 트랜잭션의 모든 연산이 다 성공하거나 다 실패하는 원자성. 송금에서 출금만 되고 입금이 안 되는 일이 없습니다. Consistency는 트랜잭션 전후 무결성 규칙이 유지되는 일관성. Isolation은 동시 실행 트랜잭션이 서로 영향을 주지 않는 격리성. Durability는 커밋된 결과가 시스템 장애에도 살아남는 영속성입니다.

연결. 10단계의 송금 시나리오 실습이 정확히 Atomicity의 예시입니다.

### D2. 트랜잭션 격리 수준 네 가지

| 수준 | dirty read | non-repeatable read | phantom read |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 막힘 | 발생 | 발생 |
| REPEATABLE READ | 막힘 | 막힘 | 발생 (대부분 DB에서 제한적) |
| SERIALIZABLE | 막힘 | 막힘 | 막힘 |

수준을 높일수록 일관성은 강해지지만 동시성은 떨어집니다. Oracle 기본은 READ COMMITTED, MySQL InnoDB 기본은 REPEATABLE READ입니다.

### D3. 정규화 1NF, 2NF, 3NF

1NF는 모든 컬럼이 원자값을 가지게 합니다(배열·리스트 컬럼 금지). 2NF는 1NF에 더해 기본 키의 일부에만 의존하는 컬럼을 분리합니다. 3NF는 2NF에 더해 기본 키가 아닌 컬럼에 의존하는 컬럼(이행적 종속)을 분리합니다.

예시. "주문 테이블에 회원이름·회원전화"가 들어 있다면 회원 정보는 회원 테이블로 분리해 3NF로 만듭니다.

### D4. 인덱스의 자료구조

B+Tree는 범위 검색에 강하고 디스크 I/O를 최소화하는 균형 트리입니다. 리프 노드가 정렬된 연결 리스트로 묶여 있어 `WHERE x > 10` 같은 범위 쿼리가 빠릅니다. 해시 인덱스는 등호 비교(`WHERE x = 10`)에서 평균 O(1)이지만 범위 검색을 못합니다.

연결. 10단계의 `CREATE INDEX` 실습 결과 `INDEX RANGE SCAN`이 나오는 이유가 B+Tree 구조 때문입니다.

### D5. NoSQL이 등장한 이유

대용량 분산 환경에서 ACID보다 가용성과 확장성을 우선해야 할 때, 스키마가 자주 바뀌는 도큐먼트 데이터를 다룰 때, 그리고 단순 key-value 캐시처럼 매우 빠른 응답이 필요할 때 NoSQL이 유리합니다. 트레이드오프는 1) 일관성 약화(eventual consistency), 2) 트랜잭션 제한, 3) 복잡한 JOIN 부재입니다.

연결. 5단계에서는 스키마 변경이 유연한 MongoDB를 사용했고, 10단계에서는 RDBMS를 요구하는 공고에 대비해 JOIN과 트랜잭션을 비교합니다.

## 자료구조

### S1. 배열과 연결 리스트의 시간 복잡도

| 연산 | 배열 | 연결 리스트 |
| --- | --- | --- |
| 접근(index로) | O(1) | O(n) |
| 탐색(값으로) | O(n) | O(n) |
| 앞쪽 삽입 | O(n) | O(1) |
| 뒤쪽 삽입(끝 포인터 있음) | O(1) 또는 O(n) | O(1) |
| 삭제(노드 포인터 있음) | O(n) | O(1) |

연결. JS의 `Array`는 사실 연결 리스트가 아니라 가변 길이 배열이지만, 앞쪽 `unshift`는 O(n)입니다.

### S2. 해시 테이블의 평균 O(1)

해시 함수가 키를 골고루 분산하면 각 버킷에 평균 1개씩 들어가므로 접근이 O(1)입니다. 충돌이 많아 한 버킷에 모두 모이면 O(n)으로 떨어집니다. 충돌 해결은 1) 체이닝(각 버킷이 연결 리스트), 2) 오픈 어드레싱(다른 빈 버킷을 찾아 저장) 두 가지가 있습니다.

연결. 자바의 `HashMap`은 체이닝을 쓰고, 한 버킷에 8개 이상 쌓이면 트리로 변환해 최악 O(log n)을 보장합니다.

### S3. 스택과 큐의 실제 쓰임

스택은 함수 호출 스택, 브라우저 뒤로가기 버튼, undo 기능 같은 LIFO 흐름에 씁니다. 큐는 메시지 큐(Kafka, RabbitMQ), 작업 큐(Celery, Bull), 너비 우선 탐색(BFS)처럼 FIFO 흐름에 씁니다.

### S4. 이진 탐색 트리의 최악 시간 복잡도

검색이 O(log n)인 이유는 매 비교마다 후보가 절반으로 줄기 때문입니다. 그러나 정렬된 데이터를 순서대로 삽입하면 트리가 한쪽으로 기울어 사실상 연결 리스트가 돼 O(n)이 됩니다. AVL과 Red-Black 트리는 삽입·삭제 후 회전(rotation)으로 균형을 유지해 항상 O(log n)을 보장합니다.

연결. 10단계 B+Tree 인덱스도 균형 트리의 한 형태입니다.

### S5. Big-O 표기법

- O(1). 카드 한 장을 꺼내는 시간. 데이터 양과 무관.
- O(log n). 사전에서 단어 찾기. 매번 후보가 절반으로.
- O(n). 책장의 책 제목을 모두 확인.
- O(n log n). 책장의 책을 제목 순으로 정렬.
- O(n²). 책장의 모든 책 쌍에 대해 짝짓기.

연결. 10단계의 인덱스 없는 검색(TABLE FULL SCAN)은 O(n)에 해당합니다.
