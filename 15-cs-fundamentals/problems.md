### N1. TCP와 UDP의 차이

TCP와 UDP의 차이 — 알맞은 설명 또는 답변 방식을 고르세요.

1. TCP는 바이트 스트림의 순서와 재전송을 제공하고 UDP는 이를 자체 보장하지 않는다.
2. UDP만 연결 설정을 하고 TCP는 비연결형이다.
3. TCP와 UDP 모두 손실된 데이터를 반드시 재전송한다.
4. UDP를 쓰면 애플리케이션에서 신뢰성을 추가할 수 없다.

<details>
<summary>정답·해설 확인</summary>

**정답: 1번**

TCP는 연결 기반 신뢰성 전송을 제공하며 UDP는 데이터그램 전달 방식입니다. 실제 지연은 환경과 구현에 따라 달라집니다.

</details>

### N2. 3-way handshake가 필요한 이유

3-way handshake가 필요한 이유 — 알맞은 설명 또는 답변 방식을 고르세요.

1. HTTP 본문을 압축한다.
2. 양쪽의 초기 시퀀스 번호와 연결 의사를 확인한다.
3. 서버 인증서를 검증하고 암호화 키를 만든다.
4. 도메인 이름을 IP 주소로 변환한다.

<details>
<summary>정답·해설 확인</summary>

**정답: 2번**

SYN, SYN+ACK, ACK로 TCP 연결을 설정합니다. TLS와 DNS는 별도의 역할입니다.

</details>

### N3. HTTP와 HTTPS의 차이

HTTP와 HTTPS의 차이 — 알맞은 설명 또는 답변 방식을 고르세요.

1. HTTPS는 로그인 권한 검사를 대신한다.
2. HTTPS는 서버에 저장된 모든 파일도 자동으로 암호화한다.
3. HTTPS는 TLS로 전송 구간의 기밀성·무결성과 서버 인증을 제공한다.
4. HTTPS를 쓰면 XSS가 발생할 수 없다.

<details>
<summary>정답·해설 확인</summary>

**정답: 3번**

HTTPS는 HTTP 통신을 TLS로 보호합니다. 접근 제어와 애플리케이션 취약점 방어는 별도로 필요합니다.

</details>

### N4. 캐시·연결 재사용 없는 HTTP/1.1·HTTP/2 HTTPS 요청의 흐름

캐시·연결 재사용 없는 HTTP/1.1·HTTP/2 HTTPS 요청의 흐름 — 알맞은 설명 또는 답변 방식을 고르세요.

1. 렌더링 → DNS 조회 → HTTP 응답 → TCP 연결 → TLS 연결
2. TLS 연결 → DNS 조회 → 렌더링 → TCP 연결 → HTTP 요청
3. HTTP 응답 → 렌더링 → DNS 조회 → TLS 연결 → TCP 연결
4. DNS 조회 → TCP 연결 → TLS 연결 → HTTP 요청·응답 → 문서 파싱과 렌더링

<details>
<summary>정답·해설 확인</summary>

**정답: 4번**

캐시와 기존 연결을 사용하지 않는 HTTP/1.1 또는 HTTP/2 연결을 가정합니다. HTTP/3는 QUIC를 사용하므로 전송 흐름이 다릅니다.

</details>

### N5. 쿠키·세션·토큰의 관계

쿠키·세션·토큰의 관계 — 알맞은 설명 또는 답변 방식을 고르세요.

1. 쿠키는 브라우저 저장·전송 수단이고, 세션은 서버 상태를 식별하며 JWT는 서명된 클레임을 담는다.
2. 쿠키와 세션은 모두 서버에 비밀번호 원문을 저장하는 방식이다.
3. JWT payload는 기본적으로 암호화되어 아무도 읽을 수 없다.
4. JWT를 발급하면 탈취된 토큰도 자동으로 즉시 무효화된다.

<details>
<summary>정답·해설 확인</summary>

**정답: 1번**

쿠키에는 세션 ID나 토큰을 담을 수 있습니다. 일반적인 서명 JWT는 내용을 암호화하지 않으며 폐기 정책이 별도로 필요합니다.

</details>

### N6. CORS와 같은 출처 정책

CORS와 같은 출처 정책 — 알맞은 설명 또는 답변 방식을 고르세요.

2. 서버의 허용 헤더를 보고 브라우저가 다른 출처 응답의 읽기 허용 여부를 판단한다.
3. CORS는 모든 HTTP 클라이언트의 요청 전송을 차단한다.
4. 출처는 URL 경로가 다르면 항상 다르다.

<details>
<summary>정답·해설 확인</summary>

**정답: 2번**

출처는 scheme, host, port 조합입니다. CORS는 브라우저 정책이며 인증이나 권한 검사를 대신하지 않습니다.

</details>

### O1. 프로세스와 스레드

3. 프로세스는 주소 공간을 분리하고 같은 프로세스의 스레드는 메모리를 공유한다.
4. 스레드끼리 공유 메모리를 쓰면 동기화가 필요 없다.

</details>

### O2. race condition과 deadlock

race condition과 deadlock — 알맞은 설명 또는 답변 방식을 고르세요.

1. race condition은 항상 컴파일할 때 검출된다.
2. deadlock은 요청이 느리지만 반드시 끝나는 상태이다.
3. 두 현상은 모두 네트워크 대역폭 부족만으로 발생한다.
4. race condition은 실행 순서에 따라 결과가 달라지고 deadlock은 자원을 서로 기다려 진행하지 못한다.

<details>
<summary>정답·해설 확인</summary>

**정답: 4번**

공유 자원의 변경 순서와 자원 대기 관계를 구분해야 합니다. 락 순서 통일이나 원자적 연산이 상황에 따라 필요합니다.

</details>

### O3. 스택과 힙

스택과 힙 — 알맞은 설명 또는 답변 방식을 고르세요.

1. 호출 스택은 함수 실행 흐름을 관리하고 힙은 동적 객체 할당에 사용한다.
2. 재귀가 깊으면 호출 스택 사용량은 반드시 줄어든다.
3. 힙은 함수가 반환할 때 모든 객체가 무조건 삭제된다.
4. GC가 있는 언어에서는 참조가 남아도 메모리 증가가 불가능하다.

<details>
<summary>정답·해설 확인</summary>

**정답: 1번**

너무 깊은 재귀는 스택 한도를 넘을 수 있습니다. 힙 객체는 언어 런타임의 메모리 관리 규칙에 따라 해제됩니다.

</details>

3. await는 Node.js 프로세스 전체를 정지시킨다.
4. readFileSync는 항상 비동기 파일 읽기이다.

<details>

await는 해당 async 함수의 진행을 유예합니다. 긴 동기 계산이나 동기 I/O는 이벤트 루프 처리 지연을 만들 수 있습니다.

</details>

### O5. 가상 메모리와 thrashing

가상 메모리와 thrashing — 알맞은 설명 또는 답변 방식을 고르세요.

1. 가상 메모리는 물리 RAM을 무한히 증가시킨다.
2. 페이지 교체가 많을수록 CPU 계산은 항상 빨라진다.
3. 가상 주소를 물리 메모리에 매핑하며 페이지 교체가 과도하면 성능이 급격히 떨어질 수 있다.
4. 모든 프로세스는 가상 메모리에서 같은 주소의 데이터를 반드시 공유한다.

<details>
<summary>정답·해설 확인</summary>

**정답: 3번**

주소 공간 추상화와 실제 메모리 용량은 다릅니다. 잦은 페이지 입출력은 유용한 계산 시간을 줄일 수 있습니다.

</details>

### D1. ACID와 송금

ACID와 송금 — 알맞은 설명 또는 답변 방식을 고르세요.

1. 원자성은 모든 트랜잭션이 동시에 끝난다는 뜻이다.
2. 격리성은 DB를 인터넷에서 분리하는 방화벽 기능이다.
3. 일관성은 모든 복제본이 매 순간 반드시 같은 값을 갖는다는 뜻만 있다.
4. 원자성은 출금·입금을 모두 반영하거나 모두 취소하고 영속성은 커밋된 결과의 보존을 뜻한다.

<details>
<summary>정답·해설 확인</summary>

**정답: 4번**

ACID는 원자성, 일관성, 격리성, 영속성입니다. 일관성은 트랜잭션 전후 정의된 무결성 규칙의 유지를 뜻합니다.

</details>

### D2. SQL 표준의 트랜잭션 격리 수준

SQL 표준의 트랜잭션 격리 수준 — 알맞은 설명 또는 답변 방식을 고르세요.

3. REPEATABLE READ는 모든 DB에서 반드시 phantom read를 발생시킨다.
4. SERIALIZABLE은 동시 실행의 결과에 아무 제약을 두지 않는다.

<details>
<summary>정답·해설 확인</summary>

SQL 표준의 최소 보장과 DB 구현을 구분합니다. PostgreSQL의 REPEATABLE READ처럼 표준보다 강한 보장을 제공할 수 있습니다.

</details>

### D4. B+Tree와 해시 인덱스

### S1. 배열과 연결 리스트의 접근 비용

배열과 연결 리스트의 접근 비용 — 알맞은 설명 또는 답변 방식을 고르세요.

4. 값을 찾는 선형 탐색은 두 구조 모두 반드시 O(log n)이다.

</details>

### S3. 스택과 큐의 실제 쓰임

스택과 큐의 실제 쓰임 — 알맞은 설명 또는 답변 방식을 고르세요.

1. 스택은 먼저 넣은 항목을 반드시 먼저 꺼낸다.
2. 큐는 마지막에 넣은 항목을 반드시 먼저 꺼낸다.
3. 스택은 LIFO로 호출·되돌리기에, 큐는 FIFO로 작업 대기에 사용할 수 있다.
4. 스택과 큐는 모두 항목을 정렬해서만 꺼낸다.

<details>
<summary>정답·해설 확인</summary>

**정답: 3번**

LIFO는 후입선출, FIFO는 선입선출입니다. 순서 규칙을 실제 호출 스택이나 작업 큐와 연결해 이해합니다.

</details>

### S4. 이진 탐색 트리의 최악 성능

이진 탐색 트리의 최악 성능 — 알맞은 설명 또는 답변 방식을 고르세요.

1. 모든 이진 탐색 트리는 구조와 무관하게 항상 O(log n)이다.
2. 정렬된 값을 순서대로 넣으면 일반 BST가 반드시 완전 균형을 이룬다.
3. 균형 트리는 검색할 때 항상 모든 노드를 읽는다.
4. 한쪽으로 치우친 트리는 검색이 O(n)이 될 수 있고 균형 트리는 높이를 O(log n)으로 관리한다.

<details>
<summary>정답·해설 확인</summary>

**정답: 4번**

검색 비용은 트리 높이에 영향을 받습니다. AVL·Red-Black 등의 균형 조건이 최악 높이를 제한합니다.

</details>

### S5. Big-O와 전체 스캔

Big-O와 전체 스캔 — 알맞은 설명 또는 답변 방식을 고르세요.

1. n개 행을 하나씩 확인하는 선형 스캔의 작업량은 O(n)이다.
2. 전체 스캔은 데이터 수와 무관하므로 O(1)이다.
3. Big-O는 실제 응답 시간을 밀리초로 정확히 예측한다.
4. 두 중첩 반복문이 각각 n번 돌면 항상 O(log n)이다.

<details>
<summary>정답·해설 확인</summary>

**정답: 1번**

Big-O는 입력 크기에 따른 증가율을 표현합니다. 실제 시간은 I/O, 캐시, 하드웨어와 구현에도 영향을 받습니다.

</details>
