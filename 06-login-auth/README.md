# 6단계 로그인 기능

## 목표

회원가입, 로그인, JWT 인증 미들웨어를 구현하며 웹서비스 인증 흐름을 익힙니다.

## 기술을 쓰는 이유와 동작 흐름

처음 보는 용어는 [전체 기술 안내서](../technology-guide.md)와 함께 읽으세요. 아래 흐름은 실습을 이해하기 위한 안내이며, 빈칸과 완료 체크는 직접 진행합니다.

| 기술 | 무엇이고, 왜 필요한가요? | 이 실습에서는 어떻게 쓰나요? |
| --- | --- | --- |
| bcryptjs | 비밀번호를 비교용 해시 값으로 바꾸는 도구입니다. 원문 비밀번호를 저장하지 않고 로그인 입력을 확인하려고 씁니다. | [server.js](./src/server.js)의 가입·로그인 처리가 저장용 변환과 비교를 나눕니다. 해시는 암호를 풀어 원문을 돌려받는 방식이 아닙니다. |
| JWT·jsonwebtoken | JWT는 사용자 식별 정보와 서명을 담는 토큰 형식이며, jsonwebtoken은 발급·검증 도구입니다. 이후 요청에서도 로그인 결과를 확인하려고 사용합니다. | [auth.js](./src/auth.js)가 토큰의 서명과 만료를 검사합니다. 여기서 서명은 내용이 변조됐는지 확인하는 값이며, 토큰 내용 자체는 암호화되지 않습니다. |
| 인증 미들웨어 | 인증은 누구의 요청인지 확인하는 작업이고, 미들웨어는 라우트 전후의 공통 처리 함수입니다. 보호 기능마다 검사 코드를 반복하지 않게 합니다. | `requireAuth`가 통과한 요청만 `/me` 처리 함수로 넘깁니다. |
| 메모리 사용자 저장소 | 실행 중인 프로그램이 보관하는 임시 사용자 목록입니다. 이번 단계는 인증 흐름에 집중하도록 DB 연결을 생략합니다. | [users.js](./src/users.js)에 사용자가 보관되며 서버 재시작 시 사라집니다. |

**로그인 이후의 처리 순서:** 입력한 비밀번호 확인 → 토큰 발급 → 클라이언트가 다음 요청의 인증 헤더에 토큰 첨부 → 서버가 검증 → 보호 API 응답. 비밀번호 확인과 이후 토큰 확인은 서로 다른 시점의 작업입니다.

**직접 관찰하기:** [요청 모음](./requests.http)으로 토큰 없는 요청과 로그인 후 요청의 응답을 비교하고, 각각 어느 함수에서 종료되는지 찾으세요. 토큰을 읽을 수 있다는 것과 유효한 서명을 검증했다는 것은 다릅니다. 이 구분은 Career Hub 인증과 16단계 보안 학습에 이어집니다.

## 실행 방법

```bash
cd 06-login-auth
cp .env.example .env
# Windows cmd:        copy .env.example .env
# Windows PowerShell: Copy-Item .env.example .env
npm install
npm run dev
```

브라우저에서 `http://localhost:4200/health`를 열어 서버 상태를 확인하세요.

[인증 요청 모음](./requests.http)을 VS Code REST Client로 위에서 아래 순서대로 실행하거나, 같은 요청을 Postman·curl로 보내 회원가입·로그인·보호 API 응답을 확인하세요.

## 학습 순서

1. `src/users.js`에서 가입한 사용자를 어디에 보관하고 찾는지 확인합니다.
2. `src/server.js`의 문제 1에서 회원가입과 비밀번호 해시 흐름을 완성합니다.
3. `src/auth.js`의 문제 2~3에서 JWT 발급과 Authorization 헤더 검증을 연결합니다.
4. 다시 `src/server.js`로 돌아와 문제 4의 로그인 검증을 완성합니다.
5. `requests.http`에서 회원가입 → 로그인 → 토큰을 넣은 보호 API 순서로 문제 5를 확인합니다.
6. 막히면 `hints.md`의 1단계부터 3단계까지 필요한 만큼만 봅니다.
7. 그래도 해결되지 않을 때만 `answers.md`와 비교하고 다시 직접 고칩니다.

## 완료 기준

- 회원가입 시 비밀번호가 해시로 저장됩니다.
- 로그인 시 비밀번호 검증 후 토큰이 발급됩니다.
- `Authorization: Bearer 토큰` 헤더로 보호된 API에 접근할 수 있습니다.

완료로 표시하기 전 [학습 근거 4종](../student-checklist.md#단계마다-남길-4종-근거)에 실행·요청 명령, 401·409·성공 응답, 해결한 오류, 바꾼 인증 코드 위치를 기록합니다.

## 취업 연결

로그인은 대부분의 웹서비스에 들어가는 핵심 기능입니다. SI/SW 신입은 보안 전문가 수준까지 갈 필요는 없지만, 비밀번호 해시와 토큰 인증의 기본 원리를 반드시 알아야 합니다.

이 단계가 끝나면 “비밀번호를 해시로 저장하고 JWT로 보호된 API를 만들었다”고 설명할 수 있어야 합니다.

## 면접 연습

### 비밀번호를 평문으로 저장하면 안 되는 이유를 설명해보세요.

평문 비밀번호는 DB가 유출되는 순간 사용자 계정이 그대로 탈취됩니다. 많은 사용자가 같은 비밀번호를 여러 서비스에서 재사용하므로 피해가 다른 서비스까지 번질 수 있습니다. 그래서 bcrypt 같은 느린 해시 함수로 저장하고, 로그인 때 입력값을 다시 비교해야 합니다.

### JWT를 요청 헤더에 담아 보내는 이유를 설명해보세요.

JWT는 로그인한 사용자를 증명하는 토큰이므로 보호된 API 요청마다 서버에 전달해야 합니다. 보통 `Authorization: Bearer <token>` 헤더를 사용하면 요청 body나 URL에 토큰을 노출하지 않고 표준적인 방식으로 인증 정보를 보낼 수 있습니다. 서버는 이 토큰의 서명을 검증해 사용자를 식별합니다.

### 401과 409 상태 코드를 언제 쓰는지 설명해보세요.

`401 Unauthorized`는 로그인하지 않았거나 토큰이 없거나 유효하지 않을 때 사용합니다. `409 Conflict`는 요청 자체는 이해했지만 현재 서버 상태와 충돌할 때 사용합니다. 회원가입에서는 이미 등록된 이메일로 가입하려는 경우 409가 적절합니다.
