# 4단계 백엔드 Node.js

## 목표

Node.js와 Express로 게시판 API를 만들며 서버, 라우팅, 요청, 응답의 흐름을 익힙니다.

## 기술을 쓰는 이유와 동작 흐름

처음 보는 용어는 [전체 기술 안내서](../technology-guide.md)와 함께 읽으세요. 아래 흐름은 실습을 이해하기 위한 안내이며, 빈칸과 완료 체크는 직접 진행합니다.

| 기술 | 무엇이고, 왜 필요한가요? | 이 실습에서는 어떻게 쓰나요? |
| --- | --- | --- |
| Node.js | JavaScript를 브라우저 밖에서 실행하는 환경입니다. 브라우저가 보낸 요청을 계속 기다리는 서버를 실행합니다. | [server.js](./src/server.js)가 지정한 포트에서 요청을 받습니다. 포트는 같은 컴퓨터 안의 통신 창구 번호입니다. |
| Express | 요청 주소와 처리 함수를 연결하는 서버 도구입니다. 직접 통신 처리를 모두 작성하는 부담을 줄입니다. | `server.js`의 라우트(주소별 처리 규칙)가 게시글 조회·생성·수정·삭제를 구분합니다. |
| HTTP·JSON | HTTP는 요청과 응답의 약속이고, JSON은 데이터를 주고받는 텍스트 형식입니다. 화면과 서버가 같은 뜻으로 데이터를 읽게 합니다. | [requests.http](./requests.http)에서 메서드·주소·본문을 보내고 응답 상태와 본문을 확인합니다. |
| 미들웨어 | 라우트 앞이나 뒤에서 요청을 공통 처리하는 함수입니다. 모든 라우트가 같은 준비를 반복하지 않게 합니다. | JSON 본문 해석과 CORS 응답 헤더 처리가 먼저 등록됩니다. CORS는 다른 출처의 브라우저 코드가 응답을 읽도록 허용하는 규칙입니다. |

**새 글 요청의 처리 순서:** API 도구가 요청 전송 → JSON 본문 해석 → 생성 라우트 실행 → 메모리 배열에 추가 → 상태 코드와 JSON 응답 반환. API는 다른 프로그램이 기능을 요청하는 접점이며, 이 서버 자체가 게시판 HTML 화면을 만드는 것은 아닙니다.

**직접 관찰하기:** 생성 후 목록 조회와 서버 재시작 후 목록 조회를 비교하세요. 메모리는 실행 중인 프로그램의 임시 저장 공간입니다. 이 한계가 다음 MongoDB 단계에서 별도 저장소를 도입하는 이유입니다.

## 실행 방법

```bash
cd 04-node-board-api
npm install
npm run dev
```

브라우저에서 `http://localhost:4000/health`를 열어 서버 상태를 확인하세요.

[API 요청 모음](./requests.http)을 VS Code REST Client로 위에서 아래 순서대로 실행하거나, 같은 요청을 Postman·curl로 보내 CRUD 상태 코드와 응답을 확인하세요.

## 학습 순서

1. `src/server.js`의 import, Express 앱, 미들웨어, 메모리 배열을 먼저 읽습니다.
2. `problems.md`의 목록 조회 → 한 건 조회 → 생성 → 수정 → 삭제 순서로 빈칸을 채웁니다.
3. 서버를 실행하고 `/health`로 요청을 받을 준비가 됐는지 확인합니다.
4. `requests.http`를 위에서 아래로 실행하며 요청과 상태 코드를 코드 위치에 연결합니다.
5. 막히면 `hints.md`의 1단계부터 3단계까지 필요한 만큼만 봅니다.
6. 그래도 해결되지 않을 때만 `answers.md`와 비교하고 다시 직접 고칩니다.

## 완료 기준

- `GET /posts`가 게시글 목록을 반환합니다.
- `POST /posts`가 새 게시글을 추가합니다.
- `PUT /posts/:id`가 게시글을 수정합니다.
- `DELETE /posts/:id`가 게시글을 삭제합니다.

완료로 표시하기 전 [학습 근거 4종](../student-checklist.md#단계마다-남길-4종-근거)에 서버 실행·요청 명령, 응답 결과, 해결한 오류, 바꾼 라우터 위치를 기록합니다.

## 취업 연결

SI/SW 프로젝트는 화면만큼 API와 데이터 흐름을 많이 다룹니다. 이 단계에서는 HTTP 메서드, 요청 body, URL 파라미터, 상태 코드를 직접 확인하는 것이 중요합니다.

이 단계가 끝나면 “게시판 CRUD API를 Express로 만들고 HTTP 상태 코드를 구분했다”고 설명할 수 있어야 합니다.

### R04-02. 404와 201 상태 코드를 언제 쓰는지 설명해보세요.

404와 201 상태 코드를 언제 쓰는지 설명해보세요.

보기 중 알맞은 설명 또는 답변 방식 하나를 고르세요.

1. 201은 생성, 204는 본문 없는 성공, 400은 잘못된 요청, 404는 대상 없음, 500은 서버 오류이다.
2. 201은 로그인 실패이고 404는 생성 성공이다.
3. 204 응답에는 반드시 JSON 오류 본문이 있다.
4. 500은 클라이언트 입력 오류만을 뜻한다.

<details>
<summary>정답·해설 확인</summary>

**정답: 1번**

상태 코드는 응답 결과를 나타냅니다. 204에는 응답 본문을 보내지 않습니다.

</details>
